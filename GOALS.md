## Adversarial challenge log (2026-10-24)

Beliefs re-tested against raw sources rather than restated — the exercise that
falsified one of them:

- **Survived — UTF-8 `bytes`.** `é`→2, `é𝄞`→6, `👋`→4 (UTF-8, where `String.length` gives 1/3/2). Now an `api-probe` check.
- **Survived — the 60 s TTL.** `miss → hit → hit(t+30) → miss(t+62)`, in the *same* process, so it is the TTL expiring and **not** isolate churn — the distinction the audit drew.
- **Falsified — "the daily cron has not been observed."** `audit_events` carries `0 3 * * *` at `2026-10-24T03:00:33.911Z`. Corrected in README. The belief was narrative-shaped ("all those rows were the replay") and survived three documents and two commits because nobody queried the table: **"has not been observed" is a statement about our records, not about the world.**
- **Survived — retry-exhaustion → DLQ**, newly observed: a malformed body pushed onto the **events** queue moved `events backlog 1 → 0` and `DLQ 0 → 1` within 10 s, while `audit_events` stayed at 31 — three failed attempts, then the body reached the sink intact.
- **Falsified, then fixed — the degrade path.** The audit's fault injection (delete a stage's D1) gave `/stats` 200 `degraded:true` + `/audit` 503 for the **pre-migration** bundle. Re-run on the Effect-native code: `/stats` **500, empty body** and `/audit` **500** — a regression the migration introduced, because `Effect.catch` recovers typed failures but not *defects*, and a dead binding is a defect. No gate could see it (every gate runs with healthy dependencies). Fixed with `Effect.catchDefect` at both layers and re-verified by the same injection (G13). **The first pass of this very log marked this one "survived"** — because the audit's *record* of an injection existed. A record of an experiment is not the experiment; re-running it is what found the regression.
- **#1b — the Effect-native consumer does route poisoned events to the DLQ** (previously proven only for the deployed async shape): on a `test_` stage, `events backlog 1→0` and `DLQ 0→1` in 10 s — and the DLQ came out as the literal **`auditdeadletter-test-g2exp`**, exactly as G4 predicted, not the generated name.
- **#3 concurrency — reproduced, with a caveat.** 20 concurrent `/stats` on the dev server *and* the live bundle: the counter advanced by 21 (the 20 plus my own measuring call, which also increments) — none lost. But a Durable Object serialises per instance anyway, so this shows the *claim* without isolating `storage.transaction`'s share of it.
- **#4 `x-photo-created` — reproduced.** Byte-identical to the PUT response's `createdAt` and inside the request window, on both the dev server and the live bundle.
- **#5 cron recurrence — untestable today.** One `0 3 * * *` fire is on record (`2026-10-24T03:00:33Z`); the next datum is 2026-10-25 03:00Z. The *delivery* contract is verified; recurrence is pending an observation, which is a different statement from "it does not recur".
- **Methodological hole found — I diffed against a commit, not against production.** A router-vs-chain differential (39 raw request/response cases, `main` vs `7e4470a`, timestamps/counters/UUIDs normalised) found 5 differences: the two *documented* ones (`/health?x=1`, `//health`), the random `queued` UUID twice (not real differences), and **`GET /HEALTH` → 200 on the router vs 404 on the chain** — *undocumented*. Probing the **live** stage then showed it is a **third generation**: it 200s `/health?x=1` (like the router) but 404s `//health` and `/HEALTH` (like the chain) — the async bundle. A differential against the previous commit proves nothing about what is deployed; the live fingerprint is the only honest baseline. My `/health/` suspicion, meanwhile, was wrong: the chain stripped trailing slashes too.
- **Case-insensitivity, borne out and bounded.** On the router, `GET /PHOTOS/mixed` and `GET /PhOtOs/mixed` both reach the photo handler and resolve the *same* object (the key is sliced by position from the raw URL), while `/photos/MIXED` 404s (keys stay case-sensitive) and `/STATS` without a token still returns **401**. An undocumented aliasing change, not a gate leak — but a change against both prior generations (G14).
- **Found along the way —** the Queues push API takes an **object or array** for `body`, never a string (`400 Validation error: Expected object, received string at "body"`). That is why the sink had only ever been proven by *placing* messages in the DLQ rather than *routing* them there.
- **Still unexercised after all this — now stated as such rather than implied:** the **Durable Object** branch of the `catchDefect` fix (only D1 was fault-injected; a DO failure is not inducible without a synthetic binding change, so it stays unverified *by construction*); the **live** bundle's degrade behaviour (asserted since 2026-10-23, never re-injected); the **62 s TTL** as a recurring check (observed once: `miss → hit → hit(t+30) → miss(t+62)`); and cron recurrence (next datum 2026-10-25 03:00Z). The **D1** fault injection, by contrast, is now a test that runs on every main push (G12) — and the `api routes` gate is verified from its log, not its conclusion: `32/32 checks passed`.

## Standing rules for whoever picks these up

- `CONVENTIONS.md` is binding; `test/policy.test.ts` enforces it.
- `main` is expected green: `tsc --noEmit`, `pnpm test`, `pnpm test:dev`, `pnpm test:e2e`, `actionlint .github/workflows/*.yml`.
- Parallel agents get **disjoint file lists**. This repo already lost a commit to two agents sharing a branch (`REVIEW-2026-10-23.md` rule 10).
- **`pnpm test:dev` binds a fixed port (1337).** Two concurrent runs collide: the second silently binds 1338 while the suite still targets 1337, and times out with a misleading error. Serialize dev-suite runs.
- A claim is not evidence. Verify the **effect** — a deploy log, an API record, a run — not the attachment: a green `tsc` and a clean plan both said "fine" while a deploy was failing 10.9 s in.
- **Compare against production, not against the previous commit.** A differential between `main` and `7e4470a` proved the router matches the chain (bar two documented cases and one it didn't document) — and proved nothing about `deep-pass`, which is a *third* generation. When the question is "is the deployed thing OK?", probe the deployed thing.
- **"Has not been observed" describes your records, not the world.** The claim that the daily cron "has not been observed" survived three documents and two commits until someone queried `audit_events` directly and found `0 3 * * *` firing at `2026-10-24T03:00:33.911Z`. Read the raw table, the raw log, the raw metrics — and prefer "I have not looked" to "it did not happen". A green *job* likewise only means its steps passed, which is not the same as its steps *running* (G11).
- New dev tooling: read the pinned source under `node_modules/<pkg>/src`, not the docs. The docs lag it, and four "impossibilities" in this repo's own history turned out to be stale that way.
