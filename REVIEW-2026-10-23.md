## 7. Deploy semantics — what a deploy claims vs what it does

Not part of track A (whose brief is cron-only); found while re-deploying the refactor.

| Observation | Evidence | Why it matters |
| --- | --- | --- |
| `Done: 0 succeeded` means **0 resources changed — and the outputs are still written** | verified both ways: adding an output then deploying stayed at `0 succeeded` while `__stack_output__.json` gained the field; removing it and deploying dropped it again. File mtime tracked the no-op run (11:36:11), not the preceding real deploy (11:35:53) | no stale-metadata footgun. The caution is the opposite one: a "successful deploy" may mean *nothing changed*, so it is not evidence a fix shipped |
| `newSqliteClasses: []` on a redeploy is **normal**, not a dropped migration | both live versions carry `exports: {"Counter":{"type":"durable-object","storage":"sqlite"}}` | **trust `exports`, not the diff summary** — one API call settles what the log line only hints at |
| `worker.versionId` / `deploymentId` are on the type but `undefined` on a non-versioned deploy | deploy output printed `versionId: undefined, deploymentId: undefined` — **corroborated upstream**: [#2235](https://github.com/alchemy-run/alchemy/issues/2235) "Full Worker deployments return no versionId or deploymentId", filed 2026-10-13 against `alchemy@2.0.0-beta.83`, now closed | a **tracked bug**, not our design: the two outputs were removed as a workaround, and `CONVENTIONS.md` records the expiry condition — re-add them when a release carrying the fix is pinned |
| A freshly attached cron trigger does **not** fire on the next minute | measured first delivery 6m42s, 6m46s, 11m11s after attach across three scripts; `deep-pass` fired at 15:56:08 with the trigger created 15:44:57 | a short check reports "never fires" and is a **false negative** — size the window (~15 min) before concluding; the "never fires" claim in this very review was written inside that window |

The common thread: every one of these is a *claim* a deploy makes that only an effect check
disputes — which is the same lesson as the `1101` (a 500 page that named no cause) and the
scope list (a printed permission set that omitted a working permission).

## 8. The one external mechanism is now asserted, not described

Everything else in this report is verifiable by test or by our own instrumentation. The scheduler
is not: it lives outside the Worker, and on 2026-10-23 it delivered a **retired** `* * * * *`
expression for ~16 minutes after the schedule had been changed, across a redeploy, without any
error anywhere in our code. Leaving that as prose in `FAILURES.md` was the wrong resting place.

**`pnpm cron-health`** (`scripts/cron-health.ts`) compares two independent observations:

| | Source | Fields |
| --- | --- | --- |
| configured | `GET /accounts/{acct}/workers/scripts/{script}/schedules` | `cron` per trigger |
| delivered | `POST /accounts/{acct}/workers/observability/telemetry/query`, `eventType=scheduled` | `event.cron`, timestamp, `scriptVersion.id`, `outcome` |

The delivered side is the **platform's** record, not our handler's D1 rows — had the handler been
the broken part, our own rows would be missing too and the check would pass vacuously.

**The invariant: what the scheduler most recently delivered must be something we configured.**
Gating on the *newest* delivery rather than every row in the window is deliberate: a retired
expression's last fires legitimately linger in a 48-hour lookback, so failing on all of them would
fail for a day after every schedule change. Older mismatches are reported as a note, not a failure.

Enforced in three places:

- `test/cron-health.test.ts` — 8 unit tests over the decision logic, one per shape the live account
  actually produced (retired-newest, superseded-retired, stalled, empty, unconfigured, non-ok).
- `.github/workflows/cron-health.yml` — every 6 hours plus on demand, so the gap in which a one-off
  replay could hide is narrower than a daily run would leave it.
- `pnpm cron-health` — locally, with `--from/--to` for back-testing a known incident.

**Back-test, on the real incident:** `--from 2026-10-23T15:40Z --to 16:35Z` exits **1** with
`newest delivery used "* * * * *", which is not configured (["0 3 * * *"]) — the platform is
replaying a retired schedule`. It also surfaced a detail the prose version missed: the replay spans
**two script versions** (`v9aa6291a` before the redeploy, `vd549945f` after).

**What it still cannot see — stated rather than implied:**

1. **A silently skipped fire.** Cloudflare exposes deliveries, not scheduler intent, so a dropped
   invocation inside an otherwise healthy window is invisible; only the freshness bound
   (`--max-age-hours`, default 26) catches a *stall*. Proving "1 of 2 expected fires happened" would
   require parsing the cron expression into a cadence and counting — not attempted.
2. **Anything older than telemetry retention.** The window is a lookback over persisted events, so a
   long absence eventually reads as "no delivery" rather than "delivery stopped on day N".
3. **A one-off replay between two runs.** With the newest-delivery gate, a blip that a later
   legitimate fire supersedes is caught only if a run happens to observe it as newest. Six-hourly
   cadence narrows this; it does not close it. Running the check at a cadence finer than the cron
   itself is the only way to shrink it further, and that trades cost against coverage.

**Current live status: failing, correctly.** As of the newest delivery (`2026-10-23T16:28:56Z`) the
account was still emitting the retired expression, so the check exits 1 today. The next legitimate
fire — the committed `0 3 * * *` at `2026-10-24 03:00 UTC` — is what turns it green, and that is the
first moment the daily schedule is actually proven rather than assumed.
