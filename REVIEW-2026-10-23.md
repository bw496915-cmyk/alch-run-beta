## 8. The one external mechanism is now asserted, not described

Everything else in this report is verifiable by test or by our own instrumentation. The scheduler
is not: it lives outside the Worker, and on 2026-10-23 it delivered a **retired** `* * * * *`
expression for ~16 minutes after the schedule had been changed, across a redeploy, without any
error anywhere in our code. Leaving that as prose in this file was the wrong resting place.

**`pnpm cron-health`** (`scripts/cron-health.ts`) compares two independent observations:

| | Source | Fields |
| --- | --- | --- |
| configured | `GET /accounts/{acct}/workers/scripts/{script}/schedules` | `cron` per trigger |
| delivered | `POST /accounts/{acct}/workers/observability/telemetry/query`, `eventType=scheduled` | `event.cron`, timestamp, `scriptVersion.id`, `outcome` |

The delivered side is the **platform's** record, not our handler's D1 rows — had the handler been
the broken part, our own rows would be missing too and the check would pass vacuously.

**The invariant: what the scheduler most recently delivered must be something we configured.**
Gating on the *newest* delivery rather than every row in the window is deliberate: a retired
expression's last fires legitimately linger in a 48-hour lookback, so failing on all of them would
fail for a day after every schedule change. Older mismatches are reported as a note, not a failure.

Enforced in three places:

- `test/cron-health.test.ts` — 8 unit tests over the decision logic, one per shape the live account
  actually produced (retired-newest, superseded-retired, stalled, empty, unconfigured, non-ok).
- `.github/workflows/cron-health.yml` — every 6 hours plus on demand, so the gap in which a one-off
  replay could hide is narrower than a daily run would leave it. The same job runs
  `pnpm queue-health`.
- `pnpm cron-health` — locally, with `--from/--to` for back-testing a known incident.

**Back-test, on the real incident:** `--from 2026-10-23T15:40Z --to 16:35Z` exits **1** with
`newest delivery used "* * * * *", which is not configured (["0 3 * * *"]) — the platform is
replaying a retired schedule`. It also surfaced a detail the prose version missed: the replay spans
**two script versions** (`v9aa6291a` before the redeploy, `vd549945f` after).

**What it still cannot see — stated rather than implied:**

1. **A silently skipped fire.** Cloudflare exposes deliveries, not scheduler intent, so a dropped
   invocation inside an otherwise healthy window is invisible; only the freshness bound
   (`--max-age-hours`, default 26) catches a *stall*. Proving "1 of 2 expected fires happened" would
   require parsing the cron expression into a cadence and counting — not attempted.
2. **Anything older than telemetry retention.** The window is a lookback over persisted events, so a
   long absence eventually reads as "no delivery" rather than "delivery stopped on day N".
3. **A one-off replay between two runs.** With the newest-delivery gate, a blip that a later
   legitimate fire supersedes is caught only if a run happens to observe it as newest. Six-hourly
   cadence narrows this; it does not close it. Running the check at a cadence finer than the cron
   itself is the only way to shrink it further, and that trades cost against coverage.

**Current live status: failing, correctly.** As of the newest delivery (`2026-10-23T16:28:56Z`) the
account was still emitting the retired expression, so the check exits 1 today. The next legitimate
fire — the committed `0 3 * * *` at `2026-10-24 03:00 UTC` — is what turns it green, and that is the
first moment the daily schedule is actually proven rather than assumed.

### One class, four instances

Four of the failures recorded here share one mistake: **a silent failure read as success.**

| Instance | Where | What was read as success |
| --- | --- | --- |
| The cron window | §9 #8 | ten minutes of silence, reported as "never fires" |

**Residual anomaly — asserted, not described.** `deep-pass` delivery stopped after 16:06:52, stayed
silent ~16 minutes, then produced four more fires carrying the **retired** `* * * * *` expression
after a redeploy (across two script versions, as the check later showed), then went quiet at
16:28:55 — while an isolated probe fired ten consecutive minutes without stopping. That is stale
scheduler delivery in this account, not anything in the repo; the controlled trial in
[AUDIT-2026-10-23.md](./AUDIT-2026-10-23.md) §8 puts the owner on Cloudflare and the window at
**~6 minutes** for that run. `pnpm cron-health` compares the platform's *delivered* expression
against the *configured* schedule, is unit-tested, and runs every 6 hours in CI; its blind spots are
in §8 above.

**Why 8 was not a shape bug.** The first hypothesis was that `crons: [...]` + a plain `scheduled`
export is undocumented for async Workers. The `Worker.d.ts:704-716` comment and the cron doc page
both document exactly that ("This is how async (non-Effect) Workers configure Cron Triggers"). The
declaration is correct; the handler was never at fault — the measurement window was.

**Why 7 is not a code defect.** `error code: 1101` is the generic page for *any* uncaught exception,
so it carries no diagnostic value on its own: a deliberately broken Worker returns the same page
while telemetry shows the real message. Here telemetry shows the opposite — no handler ran at all.
Two consequences: the shape deviation (the class did not extend `DurableObject`) was real but
unrelated, and it is now fixed for API access, not as a bug fix.

**Technique worth keeping:** `wrangler tail` is not a record — it is a stream you can lose. The
Worker's persisted Workers Observability events are queryable after the fact via
`POST /accounts/<acct>/workers/observability/telemetry/query`, which is what recovered this
incident hours later.

## 11. Rules

1. Probe a capability with a throwaway resource; never trust a scope list or a token verifier.
2. Prefer a real API token over a single-use rotating OAuth session, and never delete a
   credential copy before re-issuing credentials elsewhere.
3. Commit messages go to a file (`-F`); backticks and `$` in `-m` are shell.
4. Verify the **effect**, not the attachment: a cron is proven by an invocation, a consumer by
   a row in D1 — never by a config field or an API listing.
5. Read `--help` for the subcommand in hand; flags are not shared.
6. Guard every method a message names, and test the empty-key and trailing-slash cases.
7. Send long-running streams (tail, watch, logs) to a file, not a pipe.
8. A transient, undocumented failure stays **open** with its reference recorded — do not
   promote a hypothesis to a root cause; and query persisted telemetry, not a lost stream.
9. Size the observation window to the mechanism: a fresh cron trigger can take 6–11 minutes to
   deliver its first event, so a five-minute check reports a false negative.
10. Parallel agents get their own branch or worktree; if they must share one, commits are
    serialized and `HEAD` is verified by content (`git show HEAD:<file>`) afterwards —
    `git log` alone will not tell you whose commit survived.
11. Probe scratch space at the **start** of a session, before the first write — not once a write has
    failed: `pnpm preflight` (`scripts/preflight.ts`) writes a nonce, reads it back, removes it and
    reports `scratch: ok | READ-ONLY`. A read-only session fails at the write, and that failure
    looks like an empty network response — the report then reads complete while missing whatever
    could not be staged. When it says degraded, the report opens with `scratch: DEGRADED` and the
    step is never retried as a network error or a bad command. Corollary: revert a mutation of a
    tracked file with `git checkout -- <file>` (or `git stash` when unrelated edits must survive),
    never a copy parked in `/tmp`; `/tmp` is not durable evidence, and the backup that "exists" in
    a read-only session is the same silent failure this rule is about. Commit intended edits before
    mutating a file: `git checkout -- <file>` restores the *whole* file, so an uncommitted edit goes
    with the mutation — which is how the first pass at this very rule discarded the limits block it
    had just added to `test/docs.test.ts`.
12. Never cite an issue as "closed" without its `state_reason` **and** the PR or commit that closed it:
    fixed, duplicate and wontfix all render as `state: closed`, and only one of them lets a
    workaround expire. **Enforced by `test/docs.test.ts`** — the workaround table's closure and
    expiry columns are asserted, not trusted.
13. A generic error page (`1101`) is a symptom, never evidence: check whether any handler ran
    (`cpuTimeMs`, exception objects, entrypoint events) before blaming the code.
14. Confirm every operation whose failure would be silent by its artifact, not its return code:
    `curl -o` by the file, a redirect by the target's contents, a deploy by the resource diff
    (`Done: 0 succeeded` means 0 changed — not "the fix shipped"), a write by reading it back.
    `pnpm preflight` applies the same check to the environment, and `scripts/cron-health.ts`
    classifies an unobservable endpoint as exit 2 instead of a failed assertion.
15. The first deploy on a newly pinned `alchemy` must go out at **100% traffic** (no
    `version.traffic`); under gradual deployment it fails with `WorkerVersionConfigError`. That
    belongs to the export-era deploy flow, not to one release, so it applies to every future pin
    bump — see `MIGRATION-beta84.md` §"One-way door" and `UPGRADE.md` step 2.

### 12.2 CLI

The README documents the `pnpm` scripts; the pin's actual tree ([docs](https://alchemy.run/cli)) is
larger:

```
alchemy
├─ deploy · plan · destroy · drift · unsafe nuke
├─ dev · logs                        (logs --tail follows live)
├─ profile  create|rename|edit|refresh|current|list|show|delete   (bare = dashboard)
├─ state    list|read|delete          (bare = explorer)
└─ provider check-env | aws bootstrap|teardown | cloudflare bootstrap|teardown|token|state logs
```

Common options the README does not name: `--stage`, `--profile`, `--env-file` (defaults `.env`),
`--yes`, `--no-input`, `--config`/`-c`. Exit codes are script-safe — `0` completed, `1` failed
(including a declined plan, and bare `profile`/`state` without a terminal), `130` cancelled. The
interactive TUI is auto-suppressed under `--no-input`, `ALCHEMY_PLAIN=1`/`ALCHEMY_NO_TUI=1`, no TTY,
`CI=1`, or an agent env var (`CLAUDECODE`, `CURSOR_AGENT`, `AIDER_MODEL`, `CODEX_CLI`) — which is
why the CI job's `alchemy plan --stage "$STAGE" --no-input` is already correct. Extra CLI surface the
README does not list: `prisma` (no Prisma here), `provider cloudflare token|teardown|state logs`, and
the *unlisted* `unsafe nuke`.

### 12.3 Redaction — documented, not a gap

`AUDIT-2026-10-23.md` §1 refutes "the admin token is absent from state", and the source explains
the shape — but it is **documented behaviour, not a defect**, and the first pass here (which called
it a candidate issue) was wrong. `State/StateEncoding.ts` defines `REDACTED_MARKER = "__redacted__"`
as a serialization *tag*: `encodeState` writes a `Redacted<T>` as `{ "__redacted__": <plaintext> }`
and the reviver rebuilds the wrapper on read (`Duration`/`Date` get `__duration__`/`__date__`).
Effect's `Redacted` protects *itself* — `JSON.stringify(Redacted.make(x))` is `"<redacted>"` — so a
value is exposed only where the encoded form is printed without revival:

- `state read` (`Cli/commands/state.ts`) prints the record with `JSON.stringify`, i.e. the encoded
  form — and the docs say so outright: *"Output uses the same encoding the store persists: redacted
  secrets are unwrapped into `{ __redacted__: ... }`"* (`alchemy.run/cli/state`). Verified by running
  it here: the record shows `"ADMIN_TOKEN": { "__redacted__": <the token> }`.
- `plan` / diff redacts: `Cli/PropertyDiff.ts` renders a changed redacted prop as `(redacted)`.

So the asymmetry is deliberate — the planner hides what the state inspector shows, because the
inspector's job is to print the persisted record (already plaintext on disk, gitignored here).
Not filed upstream; the docs already specify it.
