## 1. Shape conformance

Checked against the pinned `.d.ts` and the live docs. Beta.84 claims are *not* used as
evidence: the release post is served only from the preview host (see §5).

| Concern | Documented shape | This repo | Verdict |
| --- | --- | --- | --- |
| Stack | `Alchemy.Stack(name, { providers, state }, Effect.gen(…))` | same; `Alchemy.localState()` | ✅ conformant (local disk is the documented default) |
| Worker | async `Cloudflare.Worker("id", { main, env })` | same | ✅ documented "Async Workers" style |
| Bindings | `env: { K: resource }`; "`env` is the only option for async (non-Effect) Workers" (`Worker.d.ts:700`) | same | ✅ |
| R2 / D1+`migrations` / KV / Queue declarations | `Cloudflare.R2.Bucket("Id")`, `D1.Database("Id", { migrations })`, `KV.Namespace("Id")`, `Queues.Queue("Id")` | identical, one module per resource | ✅ |

| Durable Object class | `export class Counter extends DurableObject` from `cloudflare:workers`, exported by the entry (`DurableObject.d.ts:870-897`) | `extends DurableObject<Env>`, `override fetch`, `this.ctx` | ✅ fixed |

No concern deviates now. The only nuance is that `InferEnv` is applied to the bindings object
rather than the Worker, because the Worker form hits TS2589 once a DO binding is present (§4).

## 2. What the audit overturned

Two of my conclusions were wrong. Recording them, because the wrong one cost a work track.

| Claim | Reality |
| --- | --- |
| "`crons` + plain `scheduled` is undocumented for async workers, hence the silent cron" | Documented twice — cron doc page note and `Worker.d.ts:704-716`. The cron failure is handler/runtime, **not** shape |
| "`InferEnv` is viable — my probe compiled clean" | The probe proved nothing: without `@cloudflare/workers-types` in `tsconfig.types`, `InferEnv` resolves every binding to `any`. With it, a bogus method is `TS2339 … on type 'R2Bucket'` |

I also shipped `src/Counter.ts` as "the canonical DO" (`a6d33d8`). It was an Effect-native DO,
which an async Worker cannot bind — dead on arrival, deleted in `c673ed6`.

## 3. Defects found and fixed

The offline suite (`6a6dc0e`, 26 tests) found four real bugs and one blocker. All fixed in
`c673ed6`; the tests were rewritten to assert the corrected behaviour rather than the old.

| Defect | Fix |
| --- | --- |
| `PUT /photos` (no key) → 404 while its message named PUT; guard matched POST only | both → 400, message names the method used |
| `bytes` was `body.length` (UTF-16 code units) — `"é"` stored 2 bytes in R2, recorded as 1 | `TextEncoder().encode(body).byteLength` |
| `DELETE` reported statement success, so an absent key said `deleted: true` | affected-row count |
| unparseable KV value 500'd the index | treated as a cache miss |
| `onlyBuiltDependencies` is dead config on pnpm 11 → fresh `--frozen-lockfile` install exits 1 | `allowBuilds: { workerd: true }` |
| DO class was a bare class: no `ctx.storage.transaction`, so `bump()` was a non-atomic read-modify-write | `extends DurableObject<Env>`, `override fetch`, `ctx.storage.transaction`; no namespace or storage change |

## 7. Deploy semantics — what a deploy claims vs what it does

Not part of track A (whose brief is cron-only); found while re-deploying the refactor.

| Observation | Evidence | Why it matters |
| --- | --- | --- |
| `Done: 0 succeeded` means **0 resources changed — and the outputs are still written** | verified both ways: adding an output then deploying stayed at `0 succeeded` while `__stack_output__.json` gained the field; removing it and deploying dropped it again. File mtime tracked the no-op run (11:36:11), not the preceding real deploy (11:35:53) | no stale-metadata footgun. The caution is the opposite one: a "successful deploy" may mean *nothing changed*, so it is not evidence a fix shipped |
| `newSqliteClasses: []` on a redeploy is **normal**, not a dropped migration | both live versions carry `exports: {"Counter":{"type":"durable-object","storage":"sqlite"}}` | **trust `exports`, not the diff summary** — one API call settles what the log line only hints at |
| `worker.versionId` / `deploymentId` are on the type but `undefined` on a non-versioned deploy | deploy output printed `versionId: undefined, deploymentId: undefined` | the release blog advertises these handles; surfacing them unconditionally ships two dead fields, so they were removed |
| "Cron attached" ≠ "cron firing" | trigger listed within a minute of deploy; first `cron.fire` row ~18 minutes later | verify the effect, never the attachment (also `FAILURES.md` rule 4) |

The common thread: every one of these is a *claim* a deploy makes that only an effect check
disputes — which is the same lesson as the `1101` (a 500 page that named no cause) and the
scope list (a printed permission set that omitted a working permission).
