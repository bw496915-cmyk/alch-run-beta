# Review — 2026-10-23: shape conformance, tool failures, task scoping

Three questions: does this repo match the **documented shapes** for beta.83, what actually
**failed** and why, and what should the parallel workers do next.

---

## 1. Shape check against the beta.84 post + docs

Re-read [the release post](https://alchemy.run/blog/2026-10-22-beta-84/) and the canonical
pages for [Durable Objects](https://alchemy.run/cloudflare/compute/durable-objects/) and
[Queues](https://alchemy.run/cloudflare/messaging/queues/).

| Concern | Documented shape | This repo | Verdict |
| --- | --- | --- | --- |
| Resource declaration | `Cloudflare.R2.Bucket("Id")`, `Cloudflare.D1.Database("Id", { migrations })`, `Cloudflare.KV.Namespace("Id")`, `Cloudflare.Queues.Queue("Id")` | identical | ✅ conformant |
| Worker | two styles sanctioned: async `Cloudflare.Worker("id", { main, env })` **or** Effect-native `Cloudflare.Worker("id", { main: import.meta.url }, Effect.gen(...))` | async style, `main: "./src/Api.ts"` | ✅ sanctioned style |
| Bindings into the async worker | `env: { K: resource }` — docs note "`env` is the only option for async (non-Effect) Workers" | `env: { PHOTOS, DB, CACHE, EVENTS, COUNTER }` | ✅ conformant |
| Durable Object binding | plain-class form is documented: `env: { AGENT: Cloudflare.DurableObject("Agent", { containers: [...] }) }`, explicitly "only for a plain (async) Durable Object class the Worker hosts" | `COUNTER: Cloudflare.DurableObject("Counter", { className: "Counter" })` | ✅ conformant (plain class in `src/Api.ts`) |
| Durable Object class | the async form **is** documented: `export class Counter extends DurableObject` (from `cloudflare:workers`), exported by the entry module — `DurableObject.d.ts:870-897` | plain class **not** extending `DurableObject`, with URL-dispatched `fetch()` | ⚠️ works, but neither the documented base class nor atomic storage — see §5 |
| Queue consumer | **documented** for async workers as a plain `async queue(batch, env)` with per-message `ack()`/`retry()` (queues page, "What's the difference vs a native `queue()` handler?"), and the `Queues.Consumer` resource with `scriptName: worker.workerName` (`Consumer.d.ts:76-114`) | `Queues.Consumer` + plain `async queue(batch, env)` | ✅ conformant and proven live (audit row written by the consumer) |
| Cron | **documented for async workers too**: `crons: ["0 12 * * *"]` + a plain `scheduled` export — cron page note and `Worker.d.ts:704-716` ("This is how async (non-Effect) Workers configure Cron Triggers") | `crons: [...]` prop + plain `async scheduled(...)` | ✅ shape conformant — **so the non-firing cron is a handler/runtime bug, not a shape bug** (see §5) |

**Conclusion (superseded — see §5):** the original read was that "the correct shape is
ambiguous only for the two pieces that misbehaved — DO class style and cron declaration", and
that this was the leading hypothesis for both bugs. The shape audit falsified it: the cron
declaration is documented for async workers, and most of the other concerns are conformant.
The real defects are the **hand-written binding types** (no `ctx`, no atomic storage
access, truncated R2/Queue surfaces) and a **handler-side failure** in `scheduled()`.

## 3. Scoping for parallel workers

Five independent tracks. A and B both touch the live account, so they are pinned to
**separate stages** and told to destroy their stages; `deep-pass` is owned by **A** only,
which must restore the committed daily cron as its last act.

| Track | Owner | Writes live infra? | Deliverable |
| --- | --- | --- | --- |
| **A. Cron root cause + fix** | subagent | yes — own stage `cron-probe`; repairs `deep-pass` cron | root cause, minimal fix, observed cron fire, daily cron restored |
| **B. DO 1101 root cause** | subagent | yes — own stage `do-probe` | reproduction, shape comparison (plain class vs `extends DurableObject`, redeploy-without-migration), recommended change |
| **C. Shape conformance audit** | subagent | no (read-only) | per-file conformance table with citations, ranked deviations, minimal diffs |
| **D. Test harness + CI gate** | subagent | no | `alchemy/Test` integration test + GitHub Actions workflow (typecheck always; deploy gated) |
| **E. Failure/README record** | subagent | no | `FAILURES.md` from §2 + README revision matrix update |

Coordination rules given to every worker:

- Never run `destroy` against `deep-pass`; only the stage you own.
- `pnpm typecheck` must stay green; `git` commits only for docs/tests, never `alchemy.run.ts`
  without stating the change.
- Credentials live in `.cf-token` (gitignored) — read it, never print it, never commit it.
- Report command output verbatim rather than conclusions.

## 5. Corrections after the shape audit (supersedes §1's hypothesis)

The audit (`c5a1be50`, read-only, `.d.ts` + docs as ground truth) overturned two of my
conclusions and found four defects nobody had reported. Recorded here rather than quietly
fixed, because the wrong hypothesis was expensive to hold.

### What I got wrong

| My claim | Reality |
| --- | --- |
| "`crons: string[]` + a plain `scheduled` export is **not documented for async workers**" | **Documented twice**: the cron doc page carries a note on exactly this ("Workers whose main module exports its own `scheduled` handler can attach schedules with the Worker's `crons` prop instead"), and `Worker.d.ts:704-716` says "This is how async (non-Effect) Workers configure Cron Triggers — the entry module exports its own `scheduled` handler and this prop attaches the schedules at deploy time." **The non-firing cron is a handler/runtime bug, not a shape bug.** |
| "`InferEnv` is viable — a probe compiled clean" | My probe proved nothing: with `types: ["node"]` only, `InferEnv` resolves every binding to **`any`**. Verified by adding `@cloudflare/workers-types@5.20261022.1` to `tsconfig.types`: a bogus method is now `TS2339 … on type 'R2Bucket'`, and `get(key, { onlyIf: … })` compiles. The documented typing path **requires** that package. |
| "the two unproven pieces are the ones documented only in Effect-native form" | Half wrong. The async DO *binding* and the async *queue handler* are documented too; the async DO **class** should extend `DurableObject` from `cloudflare:workers` (`DurableObject.d.ts:870-897`), which is the real deviation. |

### What the audit confirmed as conformant

Async Worker + `env` (`Worker.d.ts:700`), R2/D1-with-`migrations`/KV/Queue declarations,
module-per-resource layout, `Queues.Consumer` + `scriptName: worker.workerName`, plain
`queue()` with per-message ack/retry, `Cloudflare.DurableObject("Counter", { className })`
under `env`, `Alchemy.localState()`. The repo was in better shape than my review implied.

### The real deviations (both now addressed or queued)

1. **Hand-written binding types** — no `ctx: ExecutionContext` (so no `ctx.waitUntil`, which
   is why cache refill and audit writes were inline), no R2 `onlyIf`/range, no
   `Queue.sendBatch`/`metrics`, no `retryAll`/`attempts`, no `storage.deleteAll`/`transaction`.
   Also made the DO counter a non-atomic `get`-then-`put`. → `workers-types` added `c673ed6`;
   the `InferEnv` adoption is the next pass.
2. **No `test/`** — the documented layout expects it. → added by track D (`6a6dc0e`, 26 tests).

### Four defects the offline fakes found (fixed in `c673ed6`)

| Defect | Fix |
| --- | --- |
| `PUT /photos` (no key) → 404, while its own message named PUT; the guard matched POST only | both methods 400, message names the method used |
| `bytes` was `body.length` (UTF-16 code units) — `"é"` stored 2 bytes in R2 but recorded as 1 | `TextEncoder().encode(body).byteLength` |
| `DELETE` reported the statement's success flag, so an absent key said `deleted: true` | affected-row count |
| unparseable KV value 500'd the index | treated as a cache miss |

Plus a CI blocker: `onlyBuiltDependencies` is dead config under pnpm 11 (it silently ignores
it and defaults `strictDepBuilds: true`), so a fresh `pnpm install --frozen-lockfile` exited
**1** — that would have failed the CI gate on every clean clone. Fixed via `allowBuilds`.

### Guidance corrections

- Named state store field is **`workerName`**, not `name`, and beta.83's `Cloudflare.state()`
  is zero-arg (both fixed in `MIGRATION-beta84.md`).
- The release post is served from **`main.alchemy.run`**; the production-domain URL 404s and
  the blog index/RSS stop at beta.83.
- Beta.84 introduces a **one-way door** for Durable Objects (declarative `exports` vs the
  legacy `migrations` flow this repo used) — documented in `MIGRATION-beta84.md`.
